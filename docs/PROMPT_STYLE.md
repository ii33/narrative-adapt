# 提示词写作风格

本文件规定 `src/narrative/prompt_defaults.py` 里所有提示词（`DEFAULT_PROMPTS` 的每一条）的写法。目标是：**让模型按原则工作，而不是背否决清单**。每条提示词都按下面五段组织，长度与口径有硬指标，改完按「验收」一节实测。

## 1. 五段结构

| 段 | 写什么 | 目标篇幅 |
| --- | --- | --- |
| ① 任务与依据 | 这一段在做什么；什么是事实来源；产出要能被谁校验 | ≤150 字 |
| ② 概念骨架 | 本任务涉及的概念**先定义**，每个概念一句话 + 一条可自检的问句 | ≤600 字 |
| ③ 判断原则 | 4–6 条，按「证据 / 边界 / 复用 / 状态 / 诚实 / 范围」这类**上位原则**写，每条一句 | ≤600 字 |
| ④ 硬约定 | 字段形状、编号、坐标系、必填项。只写程序真的会校验的 | ≤600 字 |
| ⑤ 流程与自查 | 三步以内的流程 + 常见误判（每条一句）+ 提交前自检 3–5 问 | ≤500 字 |

可选段：**关系/专题取证**（本任务专属的语义要求，四到六句）。

## 2. 写作规则

1. **定义前置**：任何概念在使用前必须出现。判据：每个术语第一次出现时，同句或前一句就有定义。
2. **先原则后细则**：先写「靠语义判断」，再写字段与工具。反过来会让细则互相抵消。
3. **一个概念只讲一次**：同一约束重复出现就是信号——要么删掉一处，要么它其实该升格为原则。
4. **否定用在必要处**：只有「不做就会被误解」的地方才用否定。同一类错误只留**一个最短反例**，不要在全文反复换说法。
5. **给自检问句，不给检查清单**：写「拿掉它前后情节是否仍成立」，不要写「请依次检查 1..7」。
6. **不写实现细节**：工具名只写到「用哪个工具、什么时候用」，不描述内部实现（谁扫字符串、谁分配编号这类只在需要解释分工时一句话）。
7. **术语与合同一致**：用 `staged`、`accepted`、`at_event`、`@1`、`quotes` 这些实际字段名，别用同义中文替代。
8. **不写时代性描述**：不出现「旧版本」「曾经」「现在改为」。
9. **风格**：中文短句，一段一件事，不用「此外/同时/另外」串接长段。

## 3. 硬指标

| 指标 | 上限/目标 |
| --- | --- |
| **单条正文字数 | 不得高于旧版**（旧版含共享附录的按扣除附录算）；超限必须在改动说明里写理由 |
| 单条正文字数 | 一般 ≤2000 字；系统提示 ≤1500 字 |
| 单段字数 | ≤150 字（细则段允许 ≤220 字） |
| 「不能」出现次数 | ≤5 |
| 概念定义位置 | 在前 1/3 内 |
| 行内重复表述 | 同一约束出现 1 次 |

超限先问自己：这条是原则还是例子？例子只保留一个。**字数是硬指标：改写不是扩写**，新增文字必须来自旧版缺失的合同点，而不是把一句话拆成三句。

## 3.1 例外

| 情形 | 处理 |
| --- | --- |
| `scene_policy` | 必须**一行一条规则**：代码用 `splitlines()` 生成 `rules` 数组，加小标题或空行分段会让标题变成一条规则。不套五段式。 |
| 随上下文下发的规则类条目 | 只写「定位 + 规则」，不写流程与自检。 |
| 不足 600 字的条目 | 不套完整五段式，写成「定位一句 + 原则/约定几条 + 自检一问」。 |
| 字段清单 | 属于工具 `inputSchema` 的字段枚举不在提示词里重复，指向 schema。 |

## 4. 反模式对照

**反例（细则堆叠，概念后置）**

> 提交草稿遵循 submit_extraction 工具 inputSchema……程序以精确引文位置生成 sequence，不手算 sequence，不填写有效期或 expirations……事件默认只提交一条有代表性的准确原文引文，不足以覆盖起因……（四百字以上的长段，概念定义在第 12 段）

**正例（原则前置，可自检）**

> 事件 E：事件是介于场景和动作之间、可独立概括的情节单元，有自身起因、推进与落点。
> 判断三问：能否独立概括成一个情节？拿掉它，前后情节是否仍然成立？它是不是只剩一连串实施步骤？
>
> 2 边界：以能否独立概括判断，不以段落、章节、句子数或动作数判断。

**反例（否定链）**：不能因换章就拆，也不能因换章就合并，不能因切片结束就收尾，也不能因为一批入库就新建同义节点……
**正例（一条原则 + 一个反例）**：连续场景与同一事件可以跨章节、切片或批次延续；换章处若仍是同一过程的实施步骤就不拆，不能把章末停顿当作完整事件的落点。

## 5. 验收

1. **静态**：`pytest -k "prompt"` 必须全绿；测试断言用**要点**（关键词或短语），不要逐字锁定整句——逐字断言会阻止措辞改进。
2. **真实**：行为类提示词（提取、复核、动作、写作）改完按 `scripts/accept_extraction_consistency.py` 的做法取证：隔离工程、真实模型、同一输入多次运行，比较**结构规模与边界重合度**，而不是只看某一次是否「跑通」。
3. **记录**：`docs/` 下留一份改动说明，写清旧版指标（字数、段落、否定词数、定义位置）、新版结构、真实验收数据与结论。
4. **版本号**：改动用例必须把该条的 `version` 加一；任务审计会记录实际使用的版本。

## 6. 修改流程

1. 读当前文本，量指标（字数/段落/「不能」数/定义位置）。
2. 按五段重写，先写概念骨架，再写原则，最后落字段与流程。
3. 更新该条 `version`。
4. 跑 `pytest -k "prompt"`；把逐字长句断言改成要点断言（合同不变）。
5. 行为类改动跑真实模型多次对照，写入 `docs/`。
6. 全量 `pytest` + `ruff` 通过后提交。
