# 技能

技能是「一段给模型看的作业说明 + 它要用到的业务组/工具」，存在用户目录、跨工程共用。
它解决的是「这次任务怎么做」，不改变「这个会话是什么角色」——后者是会话模板的事。
界面入口在**独立设置页 →「技能」分组**（启动页或工作区导航底部的「设置」都能进去）。

## 这是什么、为什么要它

模型每次看到的工具表都很长，而「做这件事的步骤」并不在工具合同里：

- 工具 schema 只回答「这个工具要什么参数」，不回答「先做哪一步、看到什么再往下走、
  什么不算完成」。
- 系统提示词里写死某一类任务的步骤，会让所有任务都背上它，也动不了（改了要重启、
  还会让提示词缓存整体失效）。
- 同一段步骤每次手打给模型，既费上下文，又每次都不一样。

技能把这段步骤存成一份可复用的文本，并在需要时用 `load_skill` 显式加载：说明只进
调用它的那一轮工具结果，工具组按既有「按需加载」机制真的打开。技能不是权限：
它点名的工具照样走 `tool_loading.resolve_tool_names` 与 `load_tools`，能不能真的
打开仍由当前会话与访问模式决定。

## 和会话模板的区别

两者都提到工具，但回答的是两个不同的问题：

| | 会话模板（`chat_templates`） | 技能（`skills`） |
| --- | --- | --- |
| 回答什么 | 这个会话是**什么角色** | 这次任务**怎么做** |
| 内容 | 系统提示词全文 + 一整套工具名单 | 一段作业说明 + 想打开的业务组/工具 |
| 何时生效 | 创建会话时一次性冻结 | 由 `load_skill` 在会话中途显式加载 |
| 会不会改系统提示词 | 就是系统提示词本身 | 不改；只作为工具结果返回给那一轮 |
| 会话中途能不能变 | 不能（`snapshot()` 抄进会话元数据） | 说明随加载那一轮生效；**工具能不能真的打开**受冻结限制 |
| 存储 | 内置模板来自代码，自定义模板在工程/应用配置里 | `~/.narrative/skills.json` |
| 谁能改 | 用户（界面/配置文件） | 用户（界面/配置文件），协作者也能用 `create_skill` 等工具自建 |

一句话：模板决定「你是提取员还是编剧」，技能决定「这次提取/这次改写按哪套步骤走」。

## 放在哪

| 文件 | 默认位置 | 作用 |
| --- | --- | --- |
| 技能清单 | `~/.narrative/skills.json` | 人手可改的唯一配置源（内置技能不写进来） |
| 损坏备份 | `skills.json.bak` | 保存时若旧文件读不懂，先备份成这个再覆盖 |

- 整体换位置用环境变量 `NARRATIVE_SKILLS_FILE`（指到文件路径）。测试与便携版靠它隔离，
  绝不碰真实用户目录。
- 界面上「配置文件：…」那一行显示的就是当前实际路径——改的是哪个文件，以它为准。
- 每次保存都是原子写（先写临时文件再替换），不会留下半个技能文件。
- 读不懂的旧文件**在读这一步就报可读错误**（不是当成空表），并且保存前会先备份成 `.bak`：
  手写的技能不能被一次保存抹掉。

## 字段

```json
{
  "version": 1,
  "skills": [
    {
      "name": "场表速查",
      "summary": "把场表写对的最小步骤",
      "instructions": "# 场表\n- 先 read_project_state…\n- 再 submit_scene_table…",
      "families": ["screenplay", "writing"],
      "tools": ["read_scene_table_context"],
      "enabled": true,
      "created_at": "2026-01-01T00:00:00Z",
      "updated_at": "2026-01-01T00:00:00Z"
    }
  ]
}
```

| 字段 | 含义 |
| --- | --- |
| `name` | 身份，唯一且不区分大小写；不能与内置技能同名（内置随程序发布，重名会让「删哪一条」变得说不清）。名字**不能改**，要换名字就另存一条。 |
| `summary` | 一句话：什么时候用这条技能。列表上一行显示它；上限 200 字符。 |
| `instructions` | 给模型看的作业说明（markdown）。上限 20000 字符——它每一轮都会进上下文，不能当成塞私货的通道。 |
| `families` | 要打开的业务组，例如 `screenplay`、`writing`、`properties`；界面里点选，选中就把这一组的工具一起打开。 |
| `tools` | 额外点名的工具名，例如 `read_scene_table_context`。业务组已经覆盖的就不必再点。 |
| `enabled` | 停用的技能不会被 `load_skill` 加载（`list_skills` 仍能看到它）。 |
| `created_at` / `updated_at` | 程序写入的时间戳，只用于显示与排查。 |
| `builtin` | **只出现在返回值里**，不写进文件：文件里自称 `builtin: true` 的一律按 `false` 处理，否则用户文件就能伪造出「删不掉」的技能。 |
| `replaces` | 这条技能的正文顶替哪一段内置提示词（条目名）。留空 = 只附加说明，不改提示词。见「[提示词技能](#提示词技能replaces)」。 |
| `workflow` | 这条技能声明的生成工作流（素描 / 风格 / 视频）。留空 = 不声明工作流。见「[生成技能](#生成技能workflow)」。 |

## 提示词技能（`replaces`）

内置提示词共 17 条（`prompt_defaults.DEFAULT_PROMPTS`：协作者系统提示、提取通用要求、
标准/精细粒度、原文提取与复核、重复事件核对、动作提取、场表、正文写作、写作快捷提示、
场级划分标准、分镜导演台、素描草图风格、分镜元素分析、业务动作摘要、资料使用指导）。
它们随程序发布、只读；想改某一处措辞，做法是**复制一条技能**顶替那一段，而不是改内置文本。

- **`replaces`**：填提示词条目名（例如 `writing`）。填错键会当场报错并列出全部可选值——
  静默保存会让人以为提示词已经换了，而实际生效的还是内置那段，比报错难查得多。
- 替换只发生在**解析时**（`prompt_registry.resolve_prompt` / `compose`）：`DEFAULT_PROMPTS`
  的文本一个字符都不改。所以提示词快照继续只核对内置文本，用户改措辞不会触发升版，
  也不会让内置提示词跟着漂移。

### 谁在生效

1. 这个键上有**启用的**技能 → 取 `updated_at` 最近的一条（时间戳相同再按名字排，结果稳定：
   界面上不会一会儿显示 A、一会儿显示 B）。
2. 一条都没有（没建过、都停用了、都删了、正文为空）→ **回落到内置原文**。
   回落是自动的：解析每次按技能文件现算，不需要清理缓存，也不会留下「残留覆盖」。
3. 同一个键存了多条技能时，只有最近更新那条生效，其余的被列在 `ignored` 里回报
   （`list_prompt_keys` 与面板都看得到）——静默丢弃会让人以为「我改的是另一条」。

技能正文留空等于把这一段**去掉**（`compose` 跳过空段），不是留下一个空行；但保存时正文
是必填项，所以这个状态一般只出现在手改文件之后。

### 版本纪律

- **改内置提示词的文本必须升 `version`**（`prompt_defaults` 里那个字符串）。提示词是数据，
  版本是它对外承诺的身份：`tests/prompt_snapshot.json` 与文档里点名的版本都按它对，
  升了版而文档不跟会直接红。
- 技能的版本就是它的 `updated_at`：改正文自动变，不用手填。所以同键多条的「谁更新」
  永远有据可依。
- `list_prompt_keys` 给的是「此刻谁在生效」：内置生效时给内置版本号，被技能顶替时给那条
  技能的更新时间戳。

### 在面板里改提示词

设置页 →「技能」→「内置提示词」区（在技能列表下方）：

- 17 条全部列出，每行是条目名、键名与当前状态：「内置生效（版本 N）」或
  「被『某条技能』覆盖」。被覆盖时点名是谁——否则用户不知道该去改哪一条。
- 每行有**「复制成我的技能」**：把这条提示词**当前生效**的全文预填成一条新技能草稿，
  默认 `replaces` 就指向这个键（不顶替任何提示词的副本只会是一段没人加载的说明）。
  预填的是此刻真正在用的文本，不是出厂那份——否则「改一处措辞」会变成「回到出厂」。
  草稿**不落盘**，改完点保存才写进技能文件。
- 编辑器的「替换提示词」一栏就是 `replaces`：留空表示只附加说明；从内置提示词复制出来的
  草稿已经填好这一栏。
- 助手也能只读地看这份清单：`list_prompt_keys`（`skill` 组，不写盘）。

## 生成技能（`workflow`）

`workflow` 让一条技能声明「这一次生成交给哪个模型、哪份工作流」。它不是权限、不是阶段：
只决定执行器把任务包里已有的东西（框图、参考图、草图、首尾帧）交给哪个服务。

### 字段

| 字段 | 必填 | 含义 |
| --- | --- | --- |
| `kind` | 是 | 生成类型，只能是 `sketch`（素描稿）、`style`（风格帧）、`video`（视频）。白名单写死：`kind` 决定下游按哪种参数形状读任务包，放过未知值只会在使用时才炸。 |
| `model` | 是 | 服务/模型标识（例如 `flux3-image-klein`）。内核**不**校验取值——那是用户与服务商之间的事，内核维护一份模型名单只会越来越过期。 |
| `license` | 否 | 许可与商用条款，原样进回执。写成能看懂的一句话，例如「FLUX Kommunity License（商用条款待确认）」。 |
| `workflow_file` | 否 | ComfyUI 工作流文件路径。相对路径按包目录（`src/narrative`）解析——随程序发布的文件就那么写，用户从哪个目录启动都一样；绝对路径原样用。 |
| `params` | 否 | 想覆盖的工作流参数。**目前没有透传通道**：记 warning，不假装用上了。 |
| `expectations` | 否 | 对这次生成的期望（画幅是否取自镜头、参考图上限、模式、分辨率、单段时长……）。它是**声明**：执行器这一轮实现不了的部分进 warning，不当开关用。 |
| 其他键 | 否 | 不认识的键宽松保留（用户自己的扩展信息不被抹掉），但不参与校验。 |

### 内置三条

随程序发布、只读，开箱即用（`skills.BUILTIN_GENERATION_SKILLS`）：

| 技能 | kind | model | license | workflow_file | expectations |
| --- | --- | --- | --- | --- | --- |
| 素描（FLUX 3 Klein） | sketch | flux3-image-klein | FLUX Kommunity License（商用条款待确认） | `workflows/storyboard_flux_klein.json` | `aspect_from_shot`、`reference_images_max: 10` |
| 风格化（Krea 2 风格参考） | style | krea-2 | Krea 2（年营收门槛，商用待确认） | 留空（本轮没有随程序发布的工作流文件，走 provider 默认流程） | `uses_style_reference` |
| 首尾帧短片（MiniMax H3） | video | MiniMax-H3 | MiniMax 商用条款待确认 | 留空（走 HTTP 服务，不读工作流文件） | `modes: ["endpoints"]`、`max_segment_ms: 2000`、`resolution: ["768P", "2K"]` |

它们的正文是**给模型的作业说明**（怎么喂框图、参考图怎么排、失败怎么办、哪些不算完成），
不是给用户看的介绍。所以加载它们不打开任何工具，只提供步骤；真正的执行入口是
`run_generation_task`。

想用自己的模型：照着其中一条新建技能（内置那条只读、不能同名），声明同一个 `kind` 并启用。
用户的技能永远压过内置。

### 执行器怎么选技能

`generation_task.select_skill(kind)`：

1. 只看**启用的**且声明了 `workflow.kind == kind` 的技能；
2. 用户技能里取 `updated_at` 最近的一条；
3. 用户一条都没有（没建过、全停用、或只声明了别的 kind）→ **回落到内置生成技能**，
   回执里 `skill.builtin=true`；
4. 连内置都没有（例如打包漏了技能模块）→ 报错，并列出当前启用的生成技能。

第 3 步是刻意的不对称：内置是「默认」，不是「最高优先」。只要用户声明了同 kind 的启用
技能，一律以用户的为准，不拿内置去比时间戳——否则换个时间戳或换台机器就可能悄悄换成
别人的模型与许可（付费/本地差别很大）。回执里标 `builtin`，就是为了让界面与助手分得清
「这是用户配的」还是「这是默认的」。

### 回执里的 `warnings`

`warnings` 回答「这一轮哪些声明**没生效**」，一条一个对象：

| `code` | 意思 | 怎么办 |
| --- | --- | --- |
| `WORKFLOW_PARAMS_UNSUPPORTED` | `workflow.params` 没有透传通道（provider 只认工作流文件与环境变量） | 把参数写进工作流文件本体 |
| `WORKFLOW_FILE_UNUSED` | 这段生成不读工作流文件（视频走 HTTP 服务） | 不用改；`workflow_file` 在视频这一轮不生效 |
| `WORKFLOW_FILE_MISSING` | 声明的文件不存在，本轮改用默认工作流 | 检查路径；相对路径按 `src/narrative` 解析 |
| `WORKFLOW_FILE_ABSENT` | 这条**内置**生成技能没有随程序发布工作流文件（风格化那条） | 想指定就在技能里写 `workflow_file` |

warning 不是失败：生成照样完成并绑定，旧图只有失败时才保留。但**不要**把带 warning 的
结果说成「工作流已经按技能里写的那样生效了」。

### 边界：软件不限制流程

生成技能只回答「这一次生成交给谁」，不回答「该不该生成、先做什么、出几帧」：

- 它不新增阶段，也不改排镜 / 场表 / 正文的既有规则：定案前后能改什么、依据哈希、并发校验
  一律照旧。
- 它不改系统提示词，不是权限：`run_generation_task` 的参数校验、绑定规则与审计全部照旧。
- 完全可以不用它：自己出图，把图用 `set_keyframe` 绑上去，链路一样通。生成技能只是把
  「已排好的镜头接到某个服务」写成可核对的数据——创作流程由用户自己安排。

`families` / `tools` 的合法取值是「当前访问模式允许模型加载的业务组与工具」：
配置写入类（密钥、会话模板、技能增删改本身）刻意不在其中——技能如果能点名它们，
就成了一条绕过会话权限的后门。不确定某个名字时用 `list_available_tools` 查。

## 怎么用界面建一条

设置页 →「技能」分组：

1. 点「新建技能」。
2. **名称**：一眼能看出用途，例如「人物一致性检查」。编辑已有技能时这一栏是只读的。
3. **摘要**：一行说明什么时候用它；列表上显示的就是这句。
4. **替换提示词**（可选）：填提示词条目名就顶替那一段内置提示词；留空表示这条技能只是
   附加说明。从「内置提示词」区复制出来的草稿已经填好这一栏（见「提示词技能」）。
5. **正文**：这是给模型看的作业说明，不是给人看的介绍。写成「先调用哪个工具、看到什么
   再往下走、什么不算完成、边界在哪」。它会整段进模型上下文。
6. **业务组**：点一下选中/取消。选中 `screenplay` 就等于把这一组工具一起带上，
   通常比逐个点名工具稳。
7. **额外工具**（可选）：搜索框按名字过滤，点一下加入；没搜索时只列已经选中的。
8. **会打开哪些工具**：实时预览。写着「不打开任何工具」说明这条技能只给说明；
   写着「解析失败」说明点名的名字在当前访问模式下解析不到，按提示改。
9. 点「保存」。保存成功会提示并立刻重读列表；失败时错误就地显示，编辑框会重新打开，
   刚填的内容还在。

列表每一行能看到：名称、摘要、启用开关、会打开多少个工具（悬停看完整清单）、
业务组/额外工具/替换的提示词/声明的工作流、「内置」标记、编辑与删除。

- **内置技能**（`builtin=true`）来自代码：编辑、删除、启用开关都是灰的，悬停会说明
  「内置技能随程序发布，不能改删」。想改内置技能的做法是照着它新建一条自定义技能。
- 删除只对自定义技能有效；删内置技能会被内核拒绝，界面把拒绝原因原样显示出来。

## 技能在会话里怎么生效

协作者在会话里加载一条技能是三步，都发生在**同一轮工具调用**里：

1. `list_skills` 看有哪些技能（名字、摘要、启用、内置、点名了什么），`read_skill`
   读某一条的完整正文和它会打开的工具。
2. `load_skill(name)`：把 `families`/`tools` 交给既有的按需加载机制真的打开工具，
   同时把 `instructions` 作为**本轮工具结果**返回。
3. 下一次模型请求的 `tools` 里就会出现这些工具的精确 schema，同一任务继续调用，
   不必再 `load_tools`。

几件它**不**做的事：

- 不重写系统提示词。说明只进那一轮的工具结果，所以不会把「一次任务的步骤」变成
  整个会话的规则，也不会让提示词缓存整体失效。
- 不增加授权。加载只是把工具**合同**放进模型视野；参数校验、并发检查、审计、访问
  模式仍然全部生效。
- 不跳过校验。工具说失败就是失败，技能不改变任何 `Operations` 的判定。

停用的技能（`enabled=false`）`load_skill` 会直接拒绝，并提示先启用或换一条。

## 冻结会话的限制

会话模板建出来的会话在创建时就把工具名单抄进了元数据（`snapshot()`），整场会话
`tools` 数组不变。因此：

- 技能点名的工具**已经在当前会话工具集里**：`load_skill` 成功，并说明「没有增长工具集」。
- 技能**不点名任何工具**（`families` 与 `tools` 都为空，只给说明）：在任何会话里都能用。
- 技能要求打开当前会话没有的工具：加载会被拒绝。这时工具结果里会**如实说明没有生效**
  （原因 + 哪些工具没打开 + 可选的替代做法：新建一个不由固定模板创建的会话、
  换一个只给说明的技能、或用 `list_available_tools` 看现有工具缺哪几个），
  而不是返回成功让模型以为工具已经可用。技能正文在那一轮不会生效，模型不能按它
  声称已经完成任何工作。

## 内置技能清单

六条，随程序发布，只读：三条「作业说明」+ 三条「生成工作流」。

| 技能 | 摘要 | 点名的组/工具 或 工作流 |
| --- | --- | --- |
| 分场与分镜 | 把已入库的剧情排成场表、写成正文，再拆成分镜 | `screenplay`、`writing`、`storyboard` |
| 人物一致性检查 | 核对人物、关系与属性有没有重复记录、错记或该失效没失效 | `properties`、`graph`、`materials` |
| 外部工具调用规范 | 用 `mcp__` 前缀的外部工具时怎么发现、怎么判读写、权限不够怎么办 | 额外工具：`list_available_tools`、`load_tools` |
| 素描（FLUX 3 Klein） | 用 FLUX 3 Klein 把框图生成为描述型工作分镜 | `workflow`：sketch / flux3-image-klein |
| 风格化（Krea 2 风格参考） | 用 Krea 2 把已定案的素描草图转成带项目风格的最终画面 | `workflow`：style / krea-2 |
| 首尾帧短片（MiniMax H3） | 用 MiniMax H3 的首尾帧模式生成一段连贯动画 | `workflow`：video / MiniMax-H3 |

三条生成技能只声明 `workflow`、不点名工具（细节见「生成技能」）；前三条不声明工作流，
所以 `run_generation_task` 不会选中它们。

它们引用的是本工程真实存在的工具名与业务组（`tests/test_skills.py` 有一条守卫用例
核对这一点），所以改工具名时那条用例会先叫。

## 生成前必须满足的条件

| 条件 | 为什么 | 现象 |
|---|---|---|
| 视频时长显式给、且是 4~15 整秒 | 服务有硬性范围，镜长往往不在其中 | 不传 `constraints.duration_ms` 就按镜长报「生成时长须为4至15整秒」 |
| 视频参考图每边 ≥256px、宽高比 0.4~2.5 | 服务对首尾帧有尺寸门槛 | 帧太小会报参考图尺寸不符 |
| **项目风格在第一次出图前填好** | 项目风格属于出图依据 | 先出素描再填风格，会立刻判「依据已变化」 |

## 常见失败怎么排查

| 现象（界面上的话） | 多半是什么 | 怎么处理 |
| --- | --- | --- |
| 技能文件 … 不是合法 JSON | 手改时少了个括号/逗号 | 按提示改好那个文件；或直接在面板里保存一次（旧文件会备份成 `.bak`） |
| 用户技能不能与内置技能同名 | 名字撞了内置六条之一 | 换个名字，例如「分场与分镜·我的改法」 |
| 技能名 X 已存在（重名不区分大小写） | 同名技能已经在文件里 | 去编辑那一条，或换名字 |
| summary / instructions 不能为空 | 编辑器里留空了必填项 | 补上；摘要一句话，正文是给模型的作业说明 |
| summary / instructions 最多 N 个字符 | 超过上限 | 摘要压到一行；正文把细则拆成另一条技能 |
| 未知业务组：… | 业务组名写错，或写进了 `tools` | 按提示里列出的可选值改 |
| 未知工具：…；其中 X 是业务组名 | 把组名写进了 `tools` | 把 X 挪到 `families` |
| 这条技能会打开 `0` 个工具，但预览写着「解析失败」 | 点名的工具在当前访问模式（普通模式）下不可加载 | 去掉宿主文件/命令类工具，或让用户切到完全访问模式 |
| 内置技能只读 / 内置技能不可删除 | 想直接改内置的六条 | 照它新建一条自定义技能（提示词那 17 条可以「复制成我的技能」） |
| 未知提示词条目：… | `replaces` 拼错，或填了不存在的键 | 按提示里列出的可选键改；留空 = 只附加说明，不改任何提示词 |
| 没有可用于 sketch 生成的技能 | 连内置生成技能都没有（打包漏了技能模块），用户也没配 | 启用一条声明了该 kind 的技能；正常情况下内置三条就在 |
| 技能里的 workflow_file 不存在（…），本轮改用默认工作流 | 路径不对（相对路径按 `src/narrative` 解析） | 改成正确的相对路径或绝对路径；`warnings` 里会记下这次没生效 |
| 面板里 0 条技能 | 技能文件被清空了（内置至少六条） | 新建一条，或把备份 `skills.json.bak` 放回来 |
| 「上次启动注册技能工具时失败：…」 | 技能模块或技能文件在启动时坏掉，那 7 个工具没注册上 | 按提示修好配置；面板仍能列出与编辑已有技能 |

## 相关代码

- `src/narrative/skills.py`：内核（存储、校验、内置技能——含 `BUILTIN_GENERATION_SKILLS`
  三条生成技能、`create/update/delete/get`）。
- `src/narrative/prompt_registry.py`：提示词位解析（`replaces` 的优先级、回落内置、
  `list_prompt_keys`）；`prompt_defaults.py` 是不变的出厂文本。
- `src/narrative/skill_tools.py`：7 个技能工具（`list_skills`、`read_skill`、
  `list_prompt_keys`、`create_skill`、`update_skill`、`delete_skill`、`load_skill`）。
- `src/narrative/generation_task.py`：生成任务包、`select_skill`（用户优先 + 内置回落）、
  执行器与 `warnings`；`storyboard_video_provider.py` 是视频模型与分辨率约束的唯一真值。
- `src/narrative/tool_loading.py`：按需加载与业务组归属（技能工具归 `skill` 组）。
- `src/narrative/native_bridge.py` 的 `skills()` / `saveSkill()` / `deleteSkill()` /
  `skillOpens()` / `duplicatePromptAsSkill()`：界面入口；写盘是毫秒级原子写，
  没有后台线程。`skills()` 同时给出 17 条提示词位（`prompt_keys`）。
- `src/narrative/qml/SkillSettingsPanel.qml`：设置页「技能」分组里的这块面板
  （技能列表 + 内置提示词区 + 编辑器，面板本身独立，由 `SettingsPage.qml` 复用）。
- `tests/test_skills.py`（内核）、`tests/test_generation_task.py`（选技能与回落、执行器）、
  `tests/test_skill_settings_ui.py`（界面）。
